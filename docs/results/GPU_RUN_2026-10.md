# Laptop GPU run, October 2026: what happened and what changed

**Status: provisional.** The ByteTrack baseline did not reproduce, so every number from this run
is on hold until the detector setup is fixed and the run is repeated. Nothing below is a result
of our method.

Machine: Panshul's laptop, RTX 3050 6 GB, WSL2, `bash run.sh all --profile laptop`, YOLOX-X
(no fallback to YOLOX-S). The run's summary is saved unchanged in
[`summary.json`](summary.json); the web app's "What we found" checks read that file.

Both false positives and missed people are much worse than ByteTrack's own numbers, while ID
switches are about the same. That pattern points at the **detections** (what goes into the
tracker), not at the tracker logic. Until the reproduction passes, no comparison between
trackers from this run should be quoted.

## The seven reported problems: what changed, what remains

### 1. ByteTrack reproduction failed (MOTA 66.4 vs 76.6)

Audit of our Stage A detector path against ByteTrack's official MOT17 ablation run
(`tools/track.py -f exps/example/mot/yolox_x_ablation.py -c bytetrack_ablation.pth.tar --fp16 --fuse`,
pinned commit `d1bf019`):

| Setting | ByteTrack | Ours before | Now |
|---|---|---|---|
| Pre-processing | letterbox, 114 padding, BGR→RGB, /255, ImageNet mean/std | same | same |
| Test size | 800×1440 | 800×1440 | same |
| NMS | 0.7 | 0.7 | same |
| Detector confidence floor | 0.01 (`--conf`, overrides the exp's 0.1) | 0.05 | same (the tracker drops < 0.1 anyway, so no effect) |
| Score | obj × cls | obj × cls | same |
| **Box clipping to the image** | **none** | **clipped** | **not clipped** (`--clip-boxes` to get the old behaviour) |
| Precision | FP16 + fused | FP16 + fused | FP16 default, **`--fp32` / `FP16=0` new** |
| track_thresh / low / new | 0.6 / 0.1 / 0.7 | same | same |
| match_thresh | 0.9 (code default; the paper text says 0.8) | 0.9 | same |
| min_box_area, w/h > 1.6 dropped | 100, yes | same | same |
| track_buffer | 30, but **14 for MOT17-05 and 25 for MOT17-13** (evaluator hack) | 30 everywhere | official config + per-sequence override in the repro check |
| Unconfirmed tracks Kalman-predicted | no | yes | `bytetrack_official.yaml`: no |
| Removal bookkeeping lag | yes | no | `bytetrack_official.yaml`: yes |
| `--mot20` (no score fusion, match 0.7) | MOT20 only | `bytetrack_mot20.yaml` | same |
| Kalman state | xyah | xywh | still xywh (known, documented deviation) |

Changed:
* `models/yolox_detector.py`: boxes are no longer clipped to the image (ByteTrack never clips;
  clipping shrank edge boxes, changed IoU and the w/h filter). The setting is recorded in each
  cache (`clip_boxes`). Post-processing is now a pure, tested function (`raw_to_tlwh`).
* FP32 option end to end: `bash run.sh all --fp32` (or `FP16=0`), `models.stage_a --no-fp16`.
* `configs/baselines/bytetrack_official.yaml` + `eval.run --seq-override` reproduce ByteTrack's
  evaluator bookkeeping. `bytetrack.yaml` (our baseline) is unchanged.
* `python -m eval.repro_check`: a one-sequence check. It audits each cache's detector settings
  against the official ones (an October cache is flagged as "clipped, re-run Stage A") and runs
  both ByteTrack configs on the val half.

What remains: none of the mismatches found is obviously big enough to explain about 10 MOTA
points on its own. **The root cause is not confirmed.** The rerun below separates the
possibilities: unclipped FP16 first, then FP32 if it still fails.

### 2. MOT17-09 ID swap after occlusion (gt 8: our #2 becomes #10)

**Provisional.** It comes from a run whose baseline does not reproduce, so it may come from the
detections. Tracker-side candidates are a lost track not being re-found within track_buffer
(30 frames) and lost tracks predicted differently from ByteTrack (see the table above). We have
no MOT17 frames or caches on the CPU box, so the swap cannot be reproduced here and **no
regression test was added**. After the rerun:
`python -m eval.repro_check ... --seq MOT17-09` and the viewer export of MOT17-09
(commands below) show whether gt 8 still switches.

### 3. Delayed assignment, K = 5: NO-GO

As reported by Panshul from the run's go/no-go output: IDSW rose from 183 (no delay) to 198
(K = 5), and boxes were held for a look-ahead on about 51% of frames. Holding on half of all
frames is not "only when ambiguous". The trigger fired whenever *any* detection in a near-tie
cluster looked occluded (v̂ < 0.5), which in crowds is almost always. (These three numbers are
from his report. They are not in summary.json, so the web app shows the method result as
"pending".)

Changed:
* The pre-registered verdict stands: **NO-GO**. `configs/ours/delayed_v2_reid.yaml` is frozen
  and unchanged.
* Delayed assignment is **off by default** everywhere (`delayed.enabled: false`) and is not used
  by any baseline or "ours" row.
* A stricter, opt-in hold condition: `delayed.trigger_require_all` (every detection in the
  cluster must look occluded, not just one), in `configs/ours/delayed_v3_strict.yaml` with
  margin 0.02 and min_gain 0.3. This is exploratory and **not pre-registered**, so it cannot
  turn the NO-GO into a GO. Tests: `tests/test_delayed.py`.

### 4. MOT20 sparsetrack delayed-assignment run timed out

The timeout was in `configs/phase3/plan.yaml` (`go_no_go_v2.replication.timeout_min: 60`),
applied per arm by `eval/phase3.py`.

Changed:
* `eval.phase3 --timeout-min DATASET=MIN` overrides it per dataset.
* `run.sh all --profile laptop` passes `--timeout-min MOT20=240`. Set
  `PHASE3_TIMEOUT_MIN_MOT20=MIN` to change it (the DGX profile keeps the plan's 60).
* It resumes: each arm's finished output is kept, so a re-run only redoes the unfinished arm. A
  timeout is now reported as "incomplete (timeout ...; re-run resumes)", not just "fail".
* Remains: the arm itself is not resumable within a run (a sequence at a time); the higher
  limit is the fix.

### 5. MOT20 CMC (GMC) files start at frame 215

Panshul's `tracker/cmc.py` change (cherry-picked as is): GMC files may number lines from any
first frame (0 or an absolute MOT frame such as 215), as long as the numbers are consecutive.
Line `i` maps to cache frame `i + 1`. It now also rejects gaps, blank lines, wrong field counts
and non-finite values. **Confirmed**: tests `test_cmc_absolute_indices_map_rows_to_local_frames`
and `test_cmc_parser_rejects_index_gaps_and_malformed_rows` (tests/test_baselines.py) pass.

### 6. The SAW_EVAL_HALF run leaked the evaluation half

Changed:
* `eval/phase3.py` now **skips** caches whose detector saw the evaluation half and lists them
  under `excluded` as "leaked, excluded". Pass `--include-leaked` to score them anyway (never as
  a headline). The laptop YOLOX-S fallback is unaffected: it is already tagged "not comparable".
* `scripts/dgx/config.env`: the default `MOT20_VARIANTS` no longer contains
  `mot20full_SAW_EVAL_HALF` (opt-in only).
* Web app: the leak check card lists that run struck through ("excluded: saw the evaluation
  half"). `cleanRuns()` filters it out of anything reported.

### 7. DanceTrack Stage A crashed on 8-digit frame names

Panshul's `models/frames.py` change (cherry-picked): the sequence's first frame decides 6
(`000001.jpg`) or 8 (`00000001.jpg`) digits. **Confirmed** with new tests in
`tests/test_stage_a.py`: both namings, a clear error naming both candidates, and an 8-digit
DanceTrack sequence going through the real Stage A writer into
`cache/DanceTrack/dancetrack/val/<seq>.npz`, the folder the plan waits for. No other change was
needed: `run.sh dancetrack` already writes there.

## Rerun on the laptop (exact commands)

```bash
cd ~/zed-ps2-tracker && git checkout main && git pull
export ZED_ROOT=$HOME/zed-ps2-stagea          # the same root as the October run

# 0. Keep the October caches for comparison. They have clipped boxes, so Stage A must redo them.
mv "$ZED_ROOT/cache" "$ZED_ROOT/cache_2026-10_clipped"

# 1. Quick one-sequence check (MOT17-09, about 5 min): Stage A, then audit + both ByteTrack configs
source scripts/dgx/common.sh && activate
mkdir -p "$ZED_ROOT/repro"
python -m models.stage_a dataset --root "$ZED_ROOT/data/MOT17/train" --glob 'MOT17-09-FRCNN' \
  --dataset MOT17 --split train --out "$ZED_ROOT/repro/fp16" \
  --det-weights "$ZED_ROOT/weights/bytetrack_ablation.pth.tar" --test-size 800 1440 \
  --conf-floor 0.05 --nms 0.7 --batch-size 1 \
  --reid-weights "$ZED_ROOT/weights/osnet_ain_x1_0_msmt17.pth" \
  --trained-on "CrowdHuman + MOT17 train first half (ByteTrack ablation)"
python -m eval.repro_check --cache-dir "$ZED_ROOT/repro/fp16" --root "$ZED_ROOT/data/MOT17" \
  --seq MOT17-09 --out "$ZED_ROOT/repro/fp16_check"
#    same sequence, October cache (expect the audit to flag clip_boxes):
python -m eval.repro_check --cache-dir "$ZED_ROOT/cache_2026-10_clipped/MOT17/ablation/train" \
  --root "$ZED_ROOT/data/MOT17" --seq MOT17-09 --out "$ZED_ROOT/repro/oct_check"
#    FP32 (rules out half precision): same Stage A command with --no-fp16 and --out .../fp32
python -m models.stage_a dataset --root "$ZED_ROOT/data/MOT17/train" --glob 'MOT17-09-FRCNN' \
  --dataset MOT17 --split train --out "$ZED_ROOT/repro/fp32" --no-fp16 \
  --det-weights "$ZED_ROOT/weights/bytetrack_ablation.pth.tar" --test-size 800 1440 \

# 2. The full run with the fixed settings (resumable; start inside tmux).
#    --force redoes every stage; leaked MOT20 detector is not cached; MOT20 replication timeout 240 min.
#    Add --fp32 only if step 1 showed FP32 changes the numbers.
bash run.sh all --profile laptop --force
cat "$ZED_ROOT/STATUS"

# 3. Full 7-sequence reproduction with ByteTrack's evaluator bookkeeping (after step 2)
source scripts/dgx/common.sh && activate
python -m eval.repro_check --cache-dir "$ZED_ROOT/stagea/cache/MOT17/ablation/train" \
  --root "$ZED_ROOT/stagea/gt/MOT17" --seq all --out "$ZED_ROOT/repro/all"

# 4. Tracker output for the two benchmark Scenario slots (MOT17-04 and MOT20-02, val half)
python -m eval.export_viewer --seq MOT17-04-FRCNN --root "$ZED_ROOT/stagea/gt/MOT17" --dataset MOT17 \
  --dets "$ZED_ROOT/stagea/cache/MOT17/ablation/train" --gates configs/gates/mot17_val_half.yaml \
  --tracker baseline=configs/baselines/bytetrack.yaml \

  --dets "$ZED_ROOT/stagea/cache/MOT20/sparsetrack_ablation/train" \

  --tracker ours=configs/ours/visibility_botsort.yaml --include-gt --out "$ZED_ROOT/scenario_export"
```

* `run.sh` is the repo-root wrapper for `scripts/dgx/run.sh` (there is no `scripts/run.sh`).
* The ingested gt and cache paths (`$ZED_ROOT/stagea/...`) follow `make ingest`'s layout. If a
  path differs on the laptop, `ls $ZED_ROOT/stagea` shows it.
* Step 4 writes viewer files (`<clip>.<tracker>.json.gz`). The two benchmark slots in the
  web app's Scenarios tab (`BENCHMARK_SLOTS` in `web/src/lib/scenarios.ts`) are still not wired

* `configs/ours/visibility_botsort.yaml` is the "ours" config used by the Scenarios tab. MOT20
  has no gate file, so its export has no crossing events.

## Tuning leak check (tau_update / tau_cost)

Checked 14 Oct 2026. Tuning used **train-half frames only**: `configs/phase3/plan.yaml` sets
`tune: {cache: MOT17/ablation/train, split: train_half}`; `eval/phase3.py::tune` passes that split
to `eval.ablate.run_entry` → `python -m eval.run --split train_half`, where `eval/run.py` calls
`eval.splits.crop_cache(..., "train_half")` (frames `1 .. N//2+1`) and `prepare_gt` writes GT for
the same range. Val half is frames `N//2+2 .. N`, so the two never overlap. No leak found. A guard
now makes `tune()` refuse any split other than `train_half` (`tests/test_phase3_tune_guard.py`).
(The detector side is tracked separately by the `saw_eval_half` flag.)
